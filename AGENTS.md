# Engram working instructions

- Keep Engram general-purpose across repositories and languages. Use external codebases locally as test inputs. Keep their names, paths, source, and identifiers out of tracked changes and commit messages. Use synthetic fixtures for committed tests and examples. Verify each external test against that repository's actual configuration before making a claim about the result.
- Prioritize the original workflow shortlist: scoped instructions, complete bounded change sets, decision-aware reviews, usable history, dependency-complete tool presets, evidence-backed area drafts, instruction ownership/freshness/maintenance, and demonstrated task usefulness. VB.NET/WebForms, JavaScript/TypeScript and SQL are useful coverage for current legacy workflow checks. General TODO membership alone does not establish priority. Preserve unrelated accepted work.
- Follow the replacement goal activated November 11 and `eval/engram-delivery-goal-20261110.json`: deliver the original research-backed backlog. First finish retained EG-14 area instruction drafting with necessary ownership/scope/overflow protections, then EG-27/31 freshness and maintenance and remaining accepted items. Preserve completed deliveries and unfinished findings. CodeMap and Blast Radius are closed for improvement except a concrete regression caused by current work or an explicit user request. This supersedes the earlier exclusive core-tool priority. Use finite acceptance criteria, verify user-facing behavior, deliver, then advance; do not replace delivery with broad audits, pilot expansion or supporting infrastructure.
- A newly discovered issue does not automatically become the next task. Record it and continue the selected original improvement unless the issue demonstrably prevents delivery. Keep one implementation item active. Kernel/SSD investigations and deletion of preexisting folders remain on hold; other unfinished items remain in the original backlog, not silently completed.
- Tests establish wanted Engram behavior. Do not add tests that merely repeat an implementation. Batch source changes before compiling a release candidate, run focused acceptance checks for that batch, and group live replacements into a verified release. Full test suites require an explicit user request.
- Push only to `origin/master`. Do not add AI attribution or coauthor trailers, or create tags.
- Preserve existing uncommitted work and commits that exist only locally.
- Reuse the existing checkout and build target. Create an isolated worktree only when needed to protect work or separate branches; record its exact path and removal condition.
- Keep temporary work in one recorded location. Do not scatter copies across drive roots, AppData, or unrelated folders, or expand scratch volumes to accommodate leftovers.
- Every test fixture owns its temporary resources and cleans them up on completion and unwinding. Close database handles before removing their directories. Do not use `mem::forget`, `TempDir::keep`, or `into_path` to avoid managing fixture lifetimes.
- If a runner intentionally retains evidence or an interrupted run leaves artifacts, record their location, purpose, and cleanup condition. A completed task includes accounting for its temporary resources.
- Existing folders are not disposable merely because their names or ages look temporary. Check unique work, ignored files, Git history, references, and active use before proposing removal. Remove registered worktrees through Git.
- The current inventory of preexisting project copies and temporary folders is read-only. Further deletion requires approval of exact paths. This does not prevent teardown of new fixtures owned by the current test run.
