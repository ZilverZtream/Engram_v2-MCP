# Tool Contract

Use MCP `tools/list` for the exact names and request schemas available to the
current client profile and registered projects. This document records workflows
and selected signatures; it is not an exhaustive generated schema. The
[enhancement specification](../AGENT_ENHANCEMENT_SPEC.md) retains design targets,
including unimplemented tool names and proposed parameter shapes. Code presence,
semantic acceptance and installed delivery are separate states; see the
[delivery goal](../eval/engram-delivery-goal-20261110.json) for retained limits.

## Area instruction evidence and drafting

Instruction reference manifests use exact declaration spelling for unformatted prose. They do not case-fold an ordinary phrase such as "resolved style" into a VB `Resolved` dependency. Explicit inline-code VB references retain case-insensitive candidate lookup, including ambiguous matches and unverified qualified suffixes. Exact-spelling prose matches remain navigation candidates; neither their presence nor their absence establishes semantic intent or exhaustive reference coverage.

Use `pre_push_audit` with `instruction_maintenance` to collect an evidence pack and then check a drafting agent's proposal. Collection needs `base_commit` and `new_instruction_targets` (each names an absent Markdown path, separate provenance path and exact `area_scope`). Supply `area_context` for bounded indexed discovery, or explicit `evidence_paths`. Omit `draft` on the first request. Existing authored instructions can be reviewed through `instruction_paths`; they are not implicitly replaced by a new area draft.

For submission, retain the collection inputs and set `draft.expected_packet_blake3` to the returned `packet_blake3`. Supply `draft.new_area_files` with grounded claims, their observed/authored/proposed classification, exact quoted citations, shared-rule references and unresolved decisions. Existing instruction targets also need explicit `draft.decisions`. A stale packet is rejected; recollect and review the changed evidence instead of merely replacing its hash. Unchanged citation hashes and quotes may be reused after confirming the current packet's scope and gaps.

Each `new_area_proposals` entry returns `instruction` and `provenance` files, their paths/content/hashes, `pair_blake3`, exact `proposed_scope`, gaps and a review status. These are proposals: `authored_files_written` remains zero. `needs_evidence` may represent a useful bounded draft with named consumer or policy gaps; it does not authorize publication or prove exhaustive coverage. Citation validity establishes source integrity, not the truth or authority of an interpretation.

For an existing drafting workflow such as OX QA, provide the returned instruction as an evidence companion and the provenance as its source record, alongside complete captured sources. Keep their project, commit/current-disk basis and gaps visible in the workflow context. The drafting/reviewing agent must preserve authored exceptions, reference shared rules instead of copying them, and keep new mandates proposed. Check the consumer's resulting draft separately: it may introduce claims absent from the checked Engram proposal. A captured-checkout run does not establish current `origin/master` applicability. Publication remains the existing workflow's separate action; Engram does not create another approval or publishing system.

The standalone impact source handoff preserves the first direct consumer's exact declaration-range read when it is an admitted callable (function, method or constructor) already in another file and the proposed route omits it. File-only hints and navigation/excerpt recoveries retain their existing handoff behavior. A route may replace that prefix only when it identifies the same selected direct node and physical generation and covers its complete bounded read in the same file/project; partial or gapped coverage is insufficient. Same-file direct bridges retain the existing cross-file route preference. Previously allocated routes, actions, witnesses and walk counts/gaps stay intact under the existing response/footer budgets. Later optional spare-space caller samples may be smaller because the restored prefix consumes bytes; omission counts still reflect the displayed sample.

Standalone compact impact and Blast summaries retain their original four preferred direct consumers and every previously allocated route, source action, frontier and count. Only after the final display and source handoff are fixed, spare bytes may append full selected direct-consumer rows in retained graph order, up to eight total and within the existing2KiB per-row/12KiB response bounds, reserving256 bytes for freshness. An oversized row is skipped without hiding later rows that fit. Added rows retain exact witnesses and literal recovery actions; the omitted count decreases accordingly. If no row fits, the original output and limit explanation remain byte-identical. Graph output and typed edit-safety assessments are unchanged; a larger sample is not exhaustive or runtime proof.

VB invocation names do not use the global source-property name fallback when semantic resolution is incomplete. Ordinary unresolved call text and positions remain available. Resolved source properties and unique expression-scoped source-property candidates remain eligible; candidate inspection stops after sixteen entries, and mixed, non-property or ambiguous candidates remain unresolved. For non-invocation syntax, including implicit calls and `With` members, a known receiver symbol or candidate prevents borrowing a global property when the member has no positive property evidence, even if the receiver's type is unresolved. An implicitly declared `For Each` local whose type is unavailable can recover a unique source property from its exact collection's semantic array element type; the control-variable symbol must match, and at most sixteen enclosing loops are inspected. Direct assignment-target members retain the existing lexical write fallback; members nested in an assignment receiver or index argument do not gain that exception. Genuinely unbound receivers retain the existing lexical fallback. These are static source observations, not runtime binding guarantees. Stored graph corrections require ordinary VB re-extraction under the updated parser identity.

Ordinary VB invocations resolved by the compiler to an admitted source method retain an exact declaration locator: project-relative path, semantic member ID, declaration line, UTF-16 span and syntax-source SHA-256. Ingestion validates it against the current cohort or selected inherited target, then stores bounded managed evidence tied to both endpoint generations, physical file hashes and parser provenance. CodeMap callable recovery and revision-admitted incoming impact revalidate this evidence on every read; stale or malformed evidence is an explicit `source_call_binding_unverified` gap, never a name/arity choice between overloads. Known-source calls whose locator is unavailable stay unresolved and cannot enter generic placeholder resolution. Interface dispatch remains a separate route; external and unbound invocations retain their existing semantics. This is a compiler-selected static declaration, not proof of runtime dispatch. Native parser contract `vb-ingestion-parser-v6` forces ordinary re-extraction before the new evidence is available. Native output admits at most1024 source-call locators per file and at most256KiB of their serialized UTF-8 JSON payloads, charging every edge including repeated targets. Each locator must also fit24KiB. Calls exceeding either budget stay unknown without a locator; file metadata reports produced/omitted calls, locator bytes and both per-file limits. The byte quota covers inner locator JSON, not the complete escaped sidecar response or compiler heap; existing response bounds remain in force. Ingestion independently admits at most262144 marked calls/128MiB estimated evidence per publication with actual-sized memory reservation, bounded inherited reads and fail-closed publication on overflow. Managed edge evidence retains at most16 proofs and32 positions per proof, disclosing truncation.

## Project tools

Script extraction records a per-file `script_call_contract` for `.ts`, `.tsx`, `.js` and `.jsx` files, including empty output. Missing or incompatible receipts require re-extraction even when source bytes are unchanged: `get_index_freshness` reports `reindex_required`, and an ordinary `update_project` replaces legacy receiver bindings and declaration-only positions. Compatible files in other languages keep their existing extraction contracts; VB continues to use its separate Roslyn provenance. The script receipt records the extraction policy used, not complete receiver binding or runtime safety. Explicit `only_paths` refresh remains available for a bounded repair and does not certify outside source freshness.

VB project extraction records the compiler environment separately from loaded parser code. The bounded Windows ASP.NET Website profile supplies matching .NET Framework 4.8 metadata and configured global imports to Roslyn, allowing implicit LINQ lambda receivers to resolve source properties without a same-name fallback. Its fingerprint covers configuration and reference contents; changes invalidate unchanged VB extraction and the warm compilation. Preparation and publication recheck that identity. A scoped `only_paths` update refuses to inherit incompatible VB peers and directs the caller to an ordinary project update. Unsupported or ambiguous environments retain explicitly identified `source_only` semantics. The base profile is `framework_only`. The optional `framework_plus_web_http` profile adds only the website bin `System.Web.Http.dll` and the declared installed `System.Net.Http` metadata after checking their identities, selected configuration bindings, bounded bytes and hashes. The pair is admitted atomically; an unavailable or unsupported HTTP addition retains the valid framework profile with an explicit reason. Discovery hashes each HTTP file through a read-locked stream and caps its metadata payload at1MiB before parsing; full reference images are loaded only after the existing reference-byte admission. This is not a total-memory ceiling for headers/reader objects. No package search or general assembly-resolution closure is performed. Other application/package references, generated types and complete build/runtime binding remain unassessed. Standalone extraction does not borrow project imports or references. These receipts improve dependency evidence; they do not establish complete impact coverage or change safety.

### Review response delivery

`pre_commit_review` defaults to a 40 KiB complete reply-text budget. Optional `max_tokens` uses `ceil(UTF-8 bytes / 4)`, including JSON escaping and Markdown wrappers; it is not provider-token or MCP transport accounting. Small responses retain their existing format.

An oversized report returns its verdict, every selected finding's index/severity/location/title, gate outcomes and coverage limits, plus `response_delivery.next_call`. Recovery does not rerun gates and does not certify the current checkout. Original `max_findings`, severity and compact/full-view limits still apply. Recover authored guidance, decision conditions and detailed evidence before resolving findings; prior decisions do not suppress them. A budget too small for the complete ledger returns an explicit minimum rather than dropping findings.

### Instruction routing coverage

Explicit `applyTo` / `globs` / `paths` scopes use Engram's existing syntax and directory authority. Counts cover existing tracked regular files and nonignored untracked files, including files not indexed yet; at most eight matching paths are shown per instruction.

`no_matching_files` is a routing/coverage warning after a complete supported inventory, not a claim that a rule is wrong. Invalid or absent explicit scopes stay distinct from zero matches. ### Request traces through interface implementations

`trace_user_request` follows compiler-backed VB interface calls through explicit
`Implements` mappings. These hops are labeled `interface_implementation_candidate`,
with caller lines, implementation clause and exact contract identity. Normal
bounded call/database expansion continues from each admitted implementation.
Both source fingerprints and selected revisions must match. The trace preserves
the interface call separately; candidates do not prove which receiver a DI
container selects, that registration executes, or that downstream effects occur.
This reuses the existing interface mapping reader and traversal limits.

The default reply budget is 16,384 estimated tokens (65,536 UTF-8 bytes).
Oversized traces retain every selected edge in `paths`, with integer `from`/`to`
references into the same trace's `path_nodes`. Handlers, source locations and
hashes, coverage gaps and runtime limitations remain inline. Detailed edge
evidence and source excerpts are deferred with explicit counts; `evidence_index`
identifies the original path. Follow `response_delivery.next_call` to recover
the exact full response through `trace_user_request(response_id, response_offset)`.
Concatenate content in byte order and verify its BLAKE3 against `response_id`.
Recovery uses the saved response without re-reading the checkout. Snapshots last
at most 24 hours or 32 newer project trace snapshots. Small replies are unchanged;
a budget too small for the complete navigation view still reports the minimum.

`trace_user_request` also returns `project_policy_sources` for the returned source
files in its loaded selected inventory, including route registrations, markup,
codebehind, controllers and downstream source. The shared instruction resolver
preserves complete authored documents, applicability, hashes and explicit
omissions. Instruction edits take effect without reindexing. Guidance describes
intended behavior; it does not prove runtime execution or code compliance.
Recheck instructions for the final edit scope. If full guidance would exceed the
navigation budget, its metadata remains inline with `status: "deferred"` and
`response_delivery.deferred_policy_sources`; recover the exact original through

### Optional ask_codebase synthesis

`ask_codebase` includes `project_policy_sources` in JSON and a repository policy
section in Markdown. The existing resolver selects authored guidance for the code
paths in the returned evidence, preserving complete text, hashes, applicability
and explicit omissions. Instruction edits take effect without reindexing. This
scope is not the final edit scope; recheck guidance when additional files are chosen.
Requests with `as_of.commit` or `as_of.branch` withhold live guidance and report
`historical_unavailable`; this tool does not resolve historical policy.

Optional synthesis receives the same policy section and may cite a source with
`evidence_id: "policy:<exact source path>"` and an exact quotation from its content.
Policy describes intended behavior, not proof that the code complies. Source
ranking and retrieval status remain unchanged; quotation checks do not establish
semantic correctness. Existing synthesis prompt limits still apply.

Named-method evidence also includes bounded same-file property, field and
constant declarations whose names appear in the method, when indexed
declarations and source budget permit. These excerpts keep types and defaults
beside the method through ranking. Each has a labeled source span; the evidence
item's `lines` still identifies the primary symbol. Name matches are context,
not verified receiver bindings or a complete dependency inventory. The primary
method retains priority within the existing 4 KB definition-body allowance.

`ask_codebase` remains a deterministic evidence report by default. Set
`synthesize: true` to request one configured text-generation call over the
returned evidence, task context, conflicts, warnings and gaps. Successful
output has `mode: "synthesized"` and `synthesis.answer`, whose statements
include evidence IDs and exact excerpt quotations. The original retrieval
status is unchanged: a generated answer does not turn partial or stale
retrieval into verified knowledge. Markdown renders statement citations;
JSON also retains their checked quotation text.

`synthesis_timeout_ms` controls generation only (default 30,000ms; clamped
1,000..120,000); `deadline_ms` continues to control retrieval. Prompts above
64 KiB are declined without generation rather than silently dropping evidence.
Answers are limited to 16 KiB, eight statements, four citations per statement
and eight unknowns. The configured provider may perform transport retries;
Engram does not retry rejected synthesis or run a model-driven search loop.

Unavailable providers, failed/timed-out generation and malformed or unsupported
citations leave `mode: "retrieval_only"`, preserve evidence and expose a reason
in `synthesis`. Citation checks verify IDs and exact quotation membership,
not semantic entailment, complete coverage, policy authority or execution.
No synthesis result is persisted as policy or used to change project files.
